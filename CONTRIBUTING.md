# Contributing

Thanks for your interest in improving the template. Read this before opening a PR.

---

## Who can merge to `main`

| Role | Can open PRs | Can merge to `main` |
|------|-------------|---------------------|
| Contributor (non-admin) | Yes | No — requires 1 approval + CI green |
| Reviewer | Yes | No — can approve, not self-merge |
| Admin | Yes | Yes — but bypass is only for emergency hotfixes |

**The only safe path to `main` is: branch → PR → CI pass → approval → squash merge.**

---

## Development workflow

1. **Branch from `main`.** Never push directly to `main`.
   ```bash
   git checkout main && git pull
   git checkout -b feat/PROJ-123-your-feature
   ```

2. **Install.**
   ```bash
   npm ci
   npx playwright install --with-deps chromium
   ```

3. **Make changes.** Keep PRs scoped — one concern per PR. See coding standards below.

4. **Run the pre-push gate locally** before opening the PR:
   ```bash
   npm run typecheck
   npm run lint
   npm run format:check
   npm run test:smoke
   ```
   Pre-commit hooks (husky + lint-staged) run automatically on `git commit`. Pre-push
   hooks run `typecheck` on `git push`.

5. **Open a PR** against `main`. Fill in the PR template completely.

6. **Wait for CI.** The `lint` and `smoke` jobs must pass before a review can be
   requested. Fix failures before asking for review.

7. **Request review from CODEOWNERS.** GitHub auto-assigns reviewers based on
   `.github/CODEOWNERS`. Do not merge until you have at least one approval.

8. **Address review comments.** Push fixup commits — the CI re-runs on every push.
   Stale approvals are dismissed automatically on new commits.

9. **Squash and merge.** The project uses squash merges to keep `main` history linear.
   Do not use "Create a merge commit" or "Rebase and merge."

## Branch naming

| Type | Pattern | Example |
|------|---------|---------|
| Feature / new test | `feat/<ticket>-<slug>` | `feat/PROJ-123-checkout-tests` |
| Bug fix | `fix/<ticket>-<slug>` | `fix/QA-456-login-selector` |
| POM addition | `pom/<page-name>` | `pom/checkout-page` |
| Dependency update | `chore/deps-<month>` | `chore/deps-may-2026` |
| Config / tooling | `chore/<slug>` | `chore/update-playwright` |

## Coding standards

Read [`CLAUDE.md`](CLAUDE.md) for the full ruleset. The non-negotiables:

**Selectors**
- Semantic only: `getByRole`, `getByLabel`, `getByPlaceholder`, `getByText`, `getByTestId`
- No CSS classes (`.btn-primary`), no XPath, no positional `nth()` without a scoped container

**Waiting**
- Never `waitForTimeout` — replace with `waitFor`, `waitForURL`, `waitForResponse`, or `expect.poll`

**Page Objects**
- Private locators — tests never touch raw `Locator` fields
- No `expect()` inside POMs — assertions belong in tests only
- Method names describe user intent: `login()`, not `clickLoginButton()`
- `waitForLoad()` is required on every page class

**Tests**
- Tag every test in the title string: `'user can log in @smoke'`
- Each test is self-contained — creates its own data via factories, no shared state
- `@smoke` tests must run in under 30 seconds each

**Types**
- No `any` — use specific types, `unknown`, or `z.infer<typeof Schema>`
- No non-null assertions on external input

**Credentials**
- Read from `process.env.*` only
- Never inline passwords, tokens, or API keys in source code

## AI-generated code

Code generated by Claude or any AI assistant follows the exact same review standard as
human-written code. The reviewer is responsible for catching:

- Missing tags on tests
- `waitForTimeout` calls
- CSS or XPath selectors
- `any` types
- Missing `waitForLoad()` on new POMs
- Credentials in source

Use `agents/jira-qa-runner.md` for structured, standards-enforcing AI test generation.
Always run the pre-push gate before committing AI-generated output:

```bash
npm run typecheck && npm run lint && npm run test:smoke
```

## Test data

- Static fixtures live in `test-data/*.json` — validated by zod at module load
  (`src/utils/testData.ts`). Adding fields means updating both the JSON and its schema.
- For per-test variable data, use the factories in `src/factories/`. They wrap `random.ts`
  to produce isolated, typed inputs.
- Passwords never live in JSON — use `process.env.TEST_USER_PASSWORD` via `getUser()`.

## Adding a test type

If you're adding a new test layer (e.g. performance, contract), follow the existing pattern:

1. Add a tag (e.g. `@perf`).
2. Create `tests/<layer>/` and document its purpose.
3. Add an npm script (`test:<layer>`).
4. Add a CI job on the right cadence.
5. Update `CLAUDE.md` tagging table and `README.md`.

## Visual baselines

Generated per-browser-per-OS. Never run `--update-snapshots` without reviewing every
changed image. See [`tests/visual/README.md`](tests/visual/README.md) for the convention.
Commit baseline PNGs alongside the PR that changes the UI.

## Dependency updates

Dependabot opens weekly PRs for Playwright, axe-core, and pinned GitHub Action SHAs.
Review and merge these if smoke passes — don't let them stack up. For manual upgrades:

```bash
npm audit --omit=dev --audit-level=high   # check for known vulns
npm outdated                              # see what's behind
```

High-severity production vulnerabilities block CI merge. Fix them, don't suppress them.

---

## Reporting issues

- **Bugs**: open an issue with steps to reproduce, expected vs actual, and the Playwright
  HTML report if relevant.
- **Security vulnerabilities**: read [`SECURITY.md`](SECURITY.md) — do not file public
  issues for vulnerabilities.
